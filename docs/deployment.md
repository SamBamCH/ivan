# Deployment: two machines

The intended setup is a **producer** (the laptop: owns the history, the models, the DraftKings Chrome
profile, the odds-api key, the timers) and a **consumer** (the server at 192.168.1.59, ssh alias
`ivan-server`, checkout `/opt/ivan/app`, service user `ivan`) that runs the web UI for someone else on
the same slates. Each has its own SQLite file; the consumer pulls one way, over ssh, when its desk's Refresh is pressed.

```
laptop (producer)                                          server (consumer)
  NFL: reference tables + models (overnight.py publishes) ◄──ssh: publish + rrsync── NFL desk Refresh from laptop ──► nfl_history.sqlite (its own working tables)
  MMA: the whole card + inputs ◄──────────────────────────────────ssh── MMA slate page Refresh from laptop ──► mma_history.sqlite
  NBA: the pool (every desk edit, Refresh, nightly.py) ◄──ssh: publish + rrsync (feed.pull_ssh)── desk Refresh from laptop ──► nba_history.sqlite
  user timers: ivan-nightly (NFL), ivan-nba-nightly, ivan-nba-archive
                                                             ivan-web (system unit): scripts/serve.py on the Tailscale IP:80
                                                                └── one site, one password: /nfl, /nba (the desk), /mma
                                                             cloudflared: https://nba.prattflix.com → the whole site
```

## The server

First-time setup, as your admin user on the server:

```bash
sudo apt install python3-venv sqlite3 rsync
git clone git@github.com:SamBamCH/ivan.git ~/ivan
sudo ~/ivan/deploy/harden_server.sh        # user ivan, checkout to /opt/ivan/app, venv from requirements-server.txt, the sandboxed unit, ufw rule
sudo -u ivan nano /opt/ivan/app/.env       # IVAN_PASSWORD_HASH (scripts/password.py), IVAN_PUBLIC=1, IVAN_FEED_SSH=sam-pratt@100.91.103.23 (the laptop's tailnet IP, `tailscale ip -4` there; the server does not resolve MagicDNS names)
sudo loginctl enable-linger ivan           # user timers survive logout
```

Then from the laptop, with an ssh alias `ivan-server` for the service user:

```bash
ssh ivan-server /opt/ivan/app/deploy/setup_nba_server.sh   # NBA dirs, schema, prints the server's ssh public key, tries the pull, restarts ivan-web
deploy/install_feed_key.sh "<that public key line>"  # on the laptop: binds the key to deploy/feed_serve.sh (publish + read-only rsync of data/feed)
sudo apt install openssh-server                      # on the laptop, once (installs and starts sshd): the server reaches it over the tailnet
ssh ivan-server 'cd /opt/ivan/app && for s in nba nfl mma; do venv/bin/python scripts/$s/feed.py pull; done'   # the first pulls (what each sport's Refresh from laptop does)
```

`requirements-server.txt` is generated by `deploy/derive_server_requirements.py` from what the NFL
pre-lock path, the web UI, the NBA desk and the feed import: no Selenium, no training extras.

### The unit

`deploy/ivan-web.service` (rendered by `install_unit.sh`) runs `scripts/serve.py --host <tailscale ip>
--port 80` as user `ivan` (the one UI, every sport; [web/README.md](web/README.md)): read-only system, writable only under `data/` and its cache, no new privileges,
private tmp, a system-call filter, the single capability to bind port 80. `Restart=always`. Jobs the UI
launches are `nice`d by the runner. `journalctl -u ivan-web -f` is the log.

### Access

- **One password** for the whole site (`IVAN_PASSWORD_HASH`, `scripts/password.py --set`; the login page at
  `/login`). With `IVAN_PUBLIC=1`, or through the tunnel, the site refuses to serve without one.
- **Tailnet**: `ufw` allows port 80 on `tailscale0` alone; invite people in the Tailscale admin console.
  `http://ivan.prattflix.com` is a public A record pointing at the Tailscale IP (resolves everywhere, routes
  only on the tailnet; on the home LAN the Pi-hole wildcard needs a local override).
- **Internet**: the Cloudflare tunnel (`sudo deploy/setup_cloudflare_tunnel.sh [hostname]`: installs
  cloudflared, creates the tunnel, writes `/etc/cloudflared/config.yml` from
  `deploy/cloudflared/config.yml.template`, refuses to finish without a password hash and `IVAN_PUBLIC=1`)
  forwards the **whole site** since 2026-10-30 (a tunnel set up before then forwards `/nba` only until the
  config is re-rendered on the server). Cloudflare caches by URL: the desk's CSV exports send `no-store`; a
  bypass-cache rule for the hostname is recommended.

## Pushing code

```bash
deploy/push.sh [ivan-server]     # rsync the working tree (not git; minus venv, data, .env) → bootstrap (deps, dirs, new tables) → kill the main pid → wait → curl answers (200, or 303 to /login)
```

It restarts `ivan-web`, which drops any running job and the desk's in-memory state. Push between
slates. The server runs whatever the laptop's working tree holds, committed or not.

## Keeping data in sync

Every sport moves the same way (`ivan.core.feed`, one spec per sport in `feed.TABLES`, one script per sport,
`scripts/<sport>/feed.py publish | pull`, one ssh key bound once on the laptop): the consumer pulls over ssh when a
button is pressed, the producer publishes on that request and never pushes.

**NFL** (`scripts/nfl/feed.py`; the NFL desk's **Refresh from laptop**, step 0 of its actions on the server): the
reference bundle is every table except the working set (`nfl_player`, `odds`, `projection_snapshot`, `lineup`,
`lineup_simulation_results`, `contest_sim_report`, which the server owns for its own slates) and MLB's, gzipped
(~24 MB), applied drop-and-replace per table, plus `data/nfl/models/` (minus `archive/`). `overnight.py` publishes
the bundle every night so the morning pull finds it ready. Safe while someone is mid-slate on the server; if the
import cannot get the lock in 30 s it fails loudly, run it again.

**MMA** (`scripts/mma/feed.py`; the slate page's **Refresh from laptop**): the whole card as the laptop holds it,
every table, with `data/mma/input`, `models` and `derived`. The server only reads it.

**NBA** (`ivan.core.feed`): the consumer pulls, nothing is pushed. Its desk's **Refresh from laptop**
(`feed.pull_ssh`, `scripts/nba/feed.py pull`) runs one ssh command on the laptop, `publish`, which the key's forced
command (`deploy/feed_serve.sh`) answers by writing the live bundle fresh (the pool as it stands, the published edits,
the projection store, the headlines), then rsyncs the laptop's `data/feed/nba/` here (the forced command serves rsync
through `rrsync`, read only, rooted at `data/feed`; only changed files move, so the reference bundle the nightly writes
travels once a day), then applies the bundles. A publish whose content did not change keeps its stamp, so a Refresh
with nothing new says so. When the consumer's bar picks a slate the laptop does not hold, the command is
`publish nba <draft group>` (`scripts/nba/feed.py pull --slate DG` there, `publish --slate DG` here): the laptop loads
that slate into its pool first (the same load as its own desk's slate pick, remembered in `active_slate.json`), so both
desks move to it; the ssh waits up to ten minutes for the load. The manifest carries a producer note (the autopilot switch, the last tick) that the
consumer's header shows. The key is the server's `~/.ssh/id_ed25519` (`deploy/setup_nba_server.sh` makes and prints
it), bound on the laptop by `deploy/install_feed_key.sh` with no shell, pty or forwarding; the laptop's sshd must be on
(`sudo apt install openssh-server`, which starts it) and reachable on the tailnet (`main-thinkpad`). Table lists and the consumer's
layering of its own edits are in [nba/overnight.md](nba/overnight.md). `scripts/nba/consumer_check.py` drives the
consumer's desk from the producer (through the tunnel or the tailnet) and checks the round trip. The older sources
still work when `IVAN_FEED_SSH` is unset: `IVAN_FEED_URL` as a directory (`file://`) or `ivan-feed.service`
(`deploy/install_nba_timers.sh --feed`) serving the bundles over HTTP.

## Timers on the producer

| Unit | Sport | Schedule | Install |
|---|---|---|---|
| `ivan-nightly.timer` | NFL | 06:30, 12:30, 18:30, persistent | `deploy/install_nightly_timer.sh [--run-now]` |
| `ivan-nba-nightly.timer` | NBA | 06:45, 12:45, 18:45, persistent | `deploy/install_nba_timers.sh` |
| `ivan-nba-archive.timer` | NBA | every 5 min, 09:00–23:59 | same |
| `ivan-nba-capture.timer` | NBA | every 15 min, 09:00–23:45; acts only with the autopilot switch on (`scripts/nba/autopilot.py`) | same |

All are **user** units rendered with this checkout's path. The NFL nightly needs the desktop session's
display for the DraftKings scrape (`PassEnvironment=DISPLAY ...`). Both nightly jobs are idempotent and
catch up after sleep. Because the live timers and the laptop's `serve.py` processes run from the working
tree, **the checkout must stay on `master`**: a review branch left checked out broke the desk and the
archive timer for two days in October 2026.

## Where things are on the server

| | |
|---|---|
| `/opt/ivan/app/data/<sport>/<sport>_history.sqlite` | the server's databases |
| `/opt/ivan/app/data/nfl/input/web/`, `output/web/`, `jobs/` | NFL uploads, outputs, job logs |
| `/opt/ivan/app/data/feed/nba/`, `data/feed-state/` | the laptop's feed as last pulled; what was last applied |
| `/opt/ivan/app/data/nba/input/published/` | the laptop's pins and grids as the base layer |
| `journalctl -u ivan-web` | logs (the pull runs inside ivan-web, on Refresh) |

## Sizing

CPU-bound and forking: `config/nfl.json → classic.lineup_generation.n_jobs`, the generate step's
worker count, `sim` sizes. The NFL classic models are ~280 MB each and load per worker; 16 GB is
comfortable. Jobs run under `nice`, so other services on the box stay responsive.

## A sandbox consumer on the server

`deploy/sandbox_server.sh up` puts a second copy of this tree at `/opt/ivan/sandbox/app` on the server in
consumer mode (its own `data/`, `.env` with `IVAN_FEED_URL` pointing at the **same** `/opt/ivan/app/data/feed`
the production desk's Refresh rsyncs from the laptop, password `sandbox`, the consumer limits) and runs it as the `ivan` user's unit
`ivan-sandbox` on `127.0.0.1:8002`, sharing the production venv (`PYTHONPATH=src` makes the sandbox's own
code win over the editable install). Reach it over an ssh tunnel: `ssh -f -N -L 8002:127.0.0.1:8002 ivan-server`,
then `http://127.0.0.1:8002/nba/`. Every route the brother's desk takes is real except the Cloudflare tunnel
and his login: his desk's Refresh fetches the laptop's feed to the server's disk, the sandbox's Refresh pulls from
there, the same server-side code serves it under `/nba`. Break it freely; his desk and data are
untouched. `status`, `pull`, `reset` (wipe the sandbox's own edits and
lineups) and `down` are the other actions; `scripts/nba/consumer_check.py --sandbox --refresh` checks it the
way it checks his desk.
